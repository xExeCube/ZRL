What this is. The 2D card_flip generalized in three.js: the image is a double-sided textured plane (the back face IS the mirror — three.js gives the flip's endpoint for free), spun about axis A — tiltable to any in-plane angle and slidable so position ±1 is the hinge-on-edge case — and optionally about axes B and C simultaneously, each with its own signed velocity. All enabled axes are fixed in the world, so the motion is RC·RB·RA (each at its own ωt): a tumble. Loading a back image replaces the mirror with a true two-faced card (the back reads unmirrored when it faces you, like a physical card — mid-flip you can tell which interpretation you are seeing, so the dancer ambiguity is deliberately traded for a playing-card). The thickness slider extrudes the card into a slab whose four walls are the image's border pixels stacked through the depth: at the front view thickness projects to zero (nothing changes), and for a CENTRED axis the slab's silhouette outline w|cosθ|+τ|sinθ| is still an even function of θ — the spinning-dancer ambiguity survives thickness exactly. In silhouette mode the walls are solid silhouette-color (a cutout's border pixels are transparent, so textured walls would vanish and the two remaining faces would wobble by an ODD offset (τ/2)sinθ — enough to reveal the spin direction; solid walls keep the ambiguity honest). Same caveat for a NON-silhouette image with transparent margins: its border pixels are alpha-0, so its slab has no visible walls and reads as two faces separated by a gap — crop such images to content if you want walls. With rationally related speeds the tumble is periodic and the gif loop closes exactly (the exporter computes the least common period from the integer speeds); with incommensurate speeds the motion is quasi-periodic and never repeats — the temporal cousin of the quasilattice. The axes render as colored lines in the view only; exports never include them. The card uses no lighting (MeshBasic): shading would add depth cues, and the whole point of the front view is that a cue-free spinning card is direction-ambiguous — drag to orbit and the ambiguity dissolves, press front view and it returns. Silhouette mode gives the spinning-dancer condition exactly as in card_flip.

The 3D beam subjects. The tribar / hex ring / double hex are hex_beam's exact cell walks built as REAL geometry — each straight beam one box of unit-cube cells — and the whole object is pre-rotated so its magic direction (1,1,1) points at the camera. So the question “does the object rotate, or the camera?” dissolves: only the relative orientation reaches the projection, and rotating the object keeps every axis/gif control working unchanged. Front view = the illusion view: the tribar's gap (L−1)(1,1,1) lies exactly along the line of sight, so the open end hides behind the near beam (Gregory's column-overlap mechanism, physically realized). A 180° spin about the default vertical centre axis is precisely the animation between the two magic viewpoints — illusion → gap reveal → the mirror-winding illusion at 180° (viewing down −(1,1,1) shows the enantiomer, the isomer4d connection). These subjects ARE lit (Lambert, one fixed key light plus a low ambient floor — the ambient is load-bearing: the third face family is edge-on to the key and would otherwise render black): a real object relights as it turns — that is the honest difference between spinning an object and spinning its image, which card_flip and tribar_spin could only fake by re-deriving shading at lattice coincidences. Silhouette mode flattens them to one unlit color: unlike the card (whose outline only squashes by cosθ), a volume's silhouette genuinely changes shape through the turn, yet the spin direction stays undecidable — the true spinning-dancer condition.
